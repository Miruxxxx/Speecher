# Нативный захват звука на Rust (WASAPI)

Статус: **единственный путь захвата** (2026-07-24). PortAudio-бэкенд удалён
вместе с зависимостью `PyAudioWPatch`; предыдущее состояние дерева сохранено в
ветке `backup/pre-rust-capture`.

## Зачем

Единственный блокер проекта — [B1](CODE_REVIEW_2026-07-15.md): PyAudioWPatch
0.2.12.7 (PortAudio, WASAPI loopback) портит кучу процесса-хозяина после 2–8
минут **простаивающего** loopback-стрима, процесс умирает с 0xc0000005 без
питоновского трейсбека. Изоляция в подпроцесс (этап 0) сделала крэш
незаметным, но не убрала: ребёнок по-прежнему падает, супервизор его
перезапускает, и в момент падения кусок звука теряется.

Нативный захват убирает саму причину: в процессе захвата больше нет ни
PortAudio, ни Python — только WASAPI и ~600 строк Rust. Старый путь не оставлен
«на всякий случай»: два бэкенда — это два набора граблей и живая зависимость от
библиотеки, которую нечем чинить (апстрим PortAudio-форка мёртв).

Побочные выгоды:

- моно 16 кГц приходит **уже готовым** — из супервизора ушли numpy-конвертация
  и soxr (их делает Rust: усреднение каналов + `rubato::Fft`), а `mp.Queue` с
  pickle'ом сырых 384 КБ/с сменился пайпом на 64 КБ/с;
- список устройств берётся у WASAPI напрямую, а не через выдуманные PortAudio
  «… [Loopback]»-входы;
- есть задел на микрофон (`--source mic`) для двухдорожечного режима
  (этап 4 в [ROADMAP.md](ROADMAP.md)).

## Как устроено

```
native/audio_capture/           крейт (cargo, edition 2024)
  src/main.rs       CLI, протокол, сторож stdin, sink в stdout
  src/capture.rs    WASAPI: выбор эндпоинта, event-driven цикл, --list-devices
  src/convert.rs    f32/i16/i24/i32 -> моно f32 (усреднение каналов)
  src/resample.rs   rubato::Fft, одно долгоживущее состояние на весь стрим
src/audio/capture_base.py       политика рестарта, запись в буфер/frame_sink
src/audio/rust_capture.py       супервизор нативного ребёнка (Popen), путь к бинарю
```

### Протокол «родитель ↔ ребёнок»

| Канал | Что несёт |
|---|---|
| stdout | только сырые little-endian f32, моно, `--sample-rate`. Ничего больше |
| stderr | по одному JSON-объекту в строке: `info` / `log` / `fatal` |
| stdin  | держится открытым; **закрытие = команда «стоп»** |
| exit   | 0 — чистый выход, 1 — ошибка настройки, 2 — отвал устройства на ходу |

Почему стоп именно через stdin: ребёнок в тишине блокируется на ожидании
события WASAPI и не может опрашивать флаги, а EOF на stdin он видит в
отдельном потоке сразу — в том числе когда родитель умер, не спросив. Это
заодно страховка от осиротевшего процесса.

Разделение потоков — не украшательство: stdout остаётся чистым байтовым
конвейером, который читается `read(8192)` без парсинга, а всё
человекочитаемое уходит в stderr и попадает в лог-события `capture`.

### Что делает Rust, а что Python

Rust отдаёт **готовое моно на целевой частоте**, поэтому питоновский
супервизор только режет байты на массивы (плюс перенос «хвоста» — чтение из
пайпа может разорвать 4-байтовый сэмпл). Downmix — среднее по всем каналам,
ровно как раньше делал `numpy.mean(axis=1)`; ресемпл — `rubato::Fft`
(FixedSync::Input, чанк ~20 мс) с состоянием на весь стрим, как soxr-стрим в
питоне: почанковый ресемпл давал бы артефакты на каждой границе.

`AUTOCONVERTPCM` у WASAPI сознательно **выключен** — иначе качеством
даунмикса и ресемпла управляла бы ОС, а не мы, и результат зависел бы от
версии Windows.

### Тишина

Политика та же, что была у PortAudio-пути: **своих кадров не выдумываем**. Idle
loopback не отдаёт пакетов вообще — значит, буфер стоит, и глобальные
таймстемпы слов (инвариант из CLAUDE.md) не съезжают. Кадры, которые WASAPI
всё-таки отдал с флагом `AUDCLNT_BUFFERFLAGS_SILENT`, пересылаются нулями:
это реальное время на таймлайне устройства, выбрасывать его нельзя.

Флаг `DATA_DISCONTINUITY` на loopback взводится при каждом пробуждении
эндпоинта после тишины, поэтому он считается, а не пугает: тревожен он только
когда растёт во время звука.

### Выбор устройства

`device_hint` — подстрока имени **эндпоинта вывода** (регистронезависимо); нет
совпадения → берётся устройство по умолчанию (с записью в лог). Раньше, на
PortAudio, хинт искался среди отдельных входов вида «… [Loopback]». На машине
разработчика `"HyperX"` попадает в `Наушники гарнитуры (HyperX Virtual Surround
Sound)` и в старой, и в новой семантике, так что конфиг менять не пришлось.

`audio_capture.exe --list-devices` печатает JSON со всеми активными
эндпоинтами (имя, id, дефолтность, mix-формат); на нём построен
`scripts/list_audio_devices.py`.

## Сборка

```powershell
cargo build --release --manifest-path native\audio_capture\Cargo.toml
```

Нужен `rustup` + `stable-x86_64-pc-windows-msvc` (линкер берётся из уже
установленной Visual Studio). Бинарь — `native/audio_capture/target/release/
audio_capture.exe`, в git не кладётся (`.gitignore`). **Без него приложение не
работает**: супервизор сразу поднимает `fatal` с путём и командой сборки —
запасного питоновского пути больше нет.

## Проверки

```powershell
cargo test --manifest-path native\audio_capture\Cargo.toml   # 14 тестов
.venv\Scripts\python -m pytest tests\ -q                     # 96 тестов
.venv\Scripts\python scripts\capture_soak.py --seconds 900
```

Питоновские тесты не требуют звука: `tests/fake_capture.py` подменяет бинарь
и говорит на том же протоколе (в том числе рвёт сэмпл между чтениями и падает
с `fatal`), а `tests/test_rust_capture.py` гоняет по нему настоящий супервизор.

### Замеры на живой машине (2026-07-24)

Замеры сделаны, пока оба пути ещё существовали (PortAudio удалён сразу после
них, см. ветку `backup/pre-rust-capture`).

Тон 440 Гц, амплитуда 0.1 — сравнение сквозное (захват → downmix → ресемпл →
буфер):

| путь захвата | получено | пик спектра | RMS |
|---|---|---|---|
| нативный (Rust) | 7.96 с | 440.0 Гц | 0.0707 |
| PortAudio (был) | 7.92 с | 440.0 Гц | 0.0707 |

Совпадение до третьего знака — замена честно drop-in.

**Soak в тишине, 15 минут, оба пути одновременно** (`capture_soak.py`, никакого
звука на устройстве): оба — 0 рестартов, 0 секунд аудио (в тишине loopback не
отдаёт кадров ни тому, ни другому), ребёнок дожил до конца.

То есть **крэш B1 в этом прогоне не воспроизвёлся и на PortAudio**. Отсюда два
честных вывода:

1. Выигрыш нативного пути на этих данных **структурный, а не измеренный**: в
   его процессе нет PortAudio, поэтому конкретный баг из §B1 там невозможен.
   Утверждать «мы поймали, как один падает, а второй нет» — нельзя.
2. Само по себе воспроизведение B1 стало ненадёжным (исторически 2–8 минут,
   один раз 7 м 40 с). Эмпирику теперь взять неоткуда — старый путь удалён;
   если понадобится, он лежит в ветке `backup/pre-rust-capture`.

Сквозной прогон приложения (`python -m src`, `engine = nemotron`): стартует,
эндпоинт и формат пишутся в лог, ошибок нет. Родителя
убили `Stop-Process -Force` — нативный ребёнок ушёл сам по EOF на stdin
(проверено счётчиком процессов: 2 → 1), осиротевших `audio_capture.exe` не
осталось.

Микрофонный путь (`--source mic`) проверен только на то, что эндпоинт
открывается и кадры идут (3.46 с аудио за 4 с стены, счётчик байтов, ничего не
записывалось).

## Что осталось открытым

- `--source mic` реализован в бинаре и прокинут в конфиг (`audio.source`), но
  двухдорожечного режима (loopback + микрофон одновременно) нет — это этап 4.
- Смена устройства вывода на ходу (наушники воткнули/вынули) не
  переподключается внутри Rust: ребёнок выходит с кодом 2, супервизор его
  поднимает заново с backoff. Осознанное решение — рестарт уже написан и
  проверен, а реконнект внутри дублировал бы его.
- Размер пакета и число каналов больше не настраиваются: захват идёт по
  периоду устройства и микширует столько каналов, сколько дал WASAPI (ключи
  `frames_per_buffer` и `max_channels` из конфига удалены вместе с PortAudio).
