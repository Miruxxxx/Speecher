# Контекст для дизайн-сессии

Самодостаточный документ: у собеседника не будет доступа к репозиторию, всё
нужное — здесь. Приложите к нему **макет v2** (тот, где есть компактный режим и
пустой экран) — это согласованная база, а не отправная точка для нового
редизайна.

---

## Задача

Есть работающее десктопное приложение и согласованный макет интерфейса. Нужно
превратить макет в **дизайн-систему, пригодную для реализации**: точные токены,
разборы компонентов, все состояния. Плюс закрыть несколько нерешённых вопросов
(список в §6).

Итог заберёт разработчик и переверстает окно по нему, не переспрашивая. Поэтому
формат ответа важнее красоты подачи — см. §7.

---

## 1. Продукт

**Speecher** — Windows-приложение, которое слушает **системный звук** (всё, что
играет в наушниках: созвон, лекция, видео) и показывает живой транскрипт в
маленьком окне поверх всех остальных окон. Плюс локальная языковая модель:
выжимка за последние N минут и ответ на последний прозвучавший вопрос.

Интерфейс русский. Пользователь один — владелец машины, не массовый продукт.

## 2. Сценарий, из которого следует всё остальное

Идёт созвон на весь экран. Пользователь смотрит **на собеседника**, а не в наше
окно. Оверлей работает как периферийное зрение: взгляд скользнул, зацепил
пропущенное слово, вернулся обратно. Раз в несколько минут — осознанное
обращение: «что он спросил?», «подведи итог».

Три следствия:

1. **Окно не должно требовать внимания.** Любой прыжок раскладки, мигание,
   анимация — это кража внимания у разговора. Это главный критерий качества.
2. **Клик — дорогая операция.** Надо увести мышь с окна собеседника, попасть,
   вернуться. Поэтому основные действия дублируются глобальными хоткеями, а
   кнопки — «когда руки свободны».
3. **Фон под окном произвольный:** тёмное видео, белый документ, светлая среда
   разработки. У окна своя подложка, она непрозрачная.

## 3. Жёсткие ограничения

Это не пожелания — это то, что сломается, если проигнорировать.

| Ограничение | Следствие для дизайна |
|---|---|
| Рендер — **PyQt6** (Qt Widgets), не веб | Нет flex/grid. Внутри текстового блока — подмножество HTML. Сложную сетку внутри строки транскрипта сделать нельзя |
| Окно **frameless**, always-on-top | Системного заголовка нет: своя титульная строка, за неё же таскают окно |
| **Два размера: 520×340 (обычный) и 360×200 (компактный)** | Всё обязано выжить в 360 px ширины. Это не «мобильная версия», а полноценный рабочий режим |
| Окно **не забирает фокус** у активного приложения | Наведение и клик — единственные события мыши, на которые можно опираться |
| Текст приходит **по одному слову**, лента едет снизу вверх | Читать движущуюся мишень — основная проблема, которую решает дизайн |
| Фон **непрозрачный** (решено) | Никакого «стекла», размытия подложки, полупрозрачных слоёв поверх видео |

**Дёшево:** свои скругления, любые цвета, свой шрифт (ttf кладётся в
репозиторий), SVG-иконки, анимация прозрачности и размера, кастомные скроллбары.

**Дорого или нельзя:** тени у окна без рамки (мерцают при перетаскивании),
размытие того, что под окном, попиксельная анимация текста на каждом новом
слове, эффекты, требующие композитинга поверх чужих окон.

## 4. Что показывает интерфейс

**Постоянно:**

- **Живой транскрипт** — главный элемент, большая часть площади. Различаются два
  вида текста: *подтверждённый* (больше не изменится) и *предварительный*
  (гипотеза последних 1–2 секунд, будет перезаписана). У одного из двух движков
  распознавания предварительного текста нет вообще — дизайн должен выживать и
  без него.
- **Три индикатора состояния** в шапке:
  1. *Захват звука*: звук идёт / тишина / ошибка. **Важно:** система отдаёт
     звук только когда что-то играет. В тишине данных нет вообще — и это
     нормальный режим, а не поломка. Отличать их обязательно, иначе молчащий
     собеседник выглядит как умершая программа.
  2. *Запись на диск*: пишется / пауза / сорвалась. Независима от захвата: пауза
     записи при живом звуке — легальное состояние.
  3. *Языковая модель*: онлайн / офлайн. Может быть офлайн всю сессию, поэтому
     не должна занимать место и требовать реакции.

**По требованию:**

- **Ответ модели** — приходит потоком, длина непредсказуема (от строки до
  абзаца). Появляется и исчезает **без сдвига транскрипта**.
- **Четыре действия:** ответить на последний вопрос, показать последний вопрос,
  выжимка за интервал, меню.
- **Меню сессии:** экспорт в Markdown/текст, копировать транскрипт, загрузить
  прошлую сессию, открыть папку, настройки, о программе.
- **Настройки:** источник звука (список устройств *вывода* — слушаем то, что
  играет), язык, модель распознавания, движок, интервал автовыжимок, хоткеи.
- **История выжимок** — отдельное окно, вертикальный список свёрнутых записей.
- **Статусные сообщения** — «модель загружается», «экспортировано в …»,
  «журнал отключён». Живут 3–5 секунд.
- **Уведомление**, когда действие вызвано хоткеем, а окно скрыто.
- **Фатальная ошибка** — после неё приложение закрывается.

**Пустой экран первого запуска** — пока ничего не играет, транскрипта нет
законно, иногда минутами.

## 5. Что уже решено — не пересматривать

Эти решения приняты и проверены; они закрывают конкретные дефекты прошлой
версии. Изменять их можно только с внятным аргументом.

1. **Состояния — пилюлями в шапке, а не баннерами.** Баннер, выскакивая, сдвигал
   контент; пилюля живёт в шапке постоянно и стоит ноль места.
2. **Ответ модели — карточкой поверх транскрипта**, не панелью снизу. Панель
   двигала ленту при появлении и исчезновении.
3. **Таймстемпы в левом жёлобе**, один на реплику. Без них полчаса разговора
   выглядят одним абзацем; инлайном они съедают колонку текста.
4. **Подписи кнопок — по-русски, человеческими словами**, а не «Last ?».
5. **Никаких системных кнопок** свернуть/развернуть: развернуть бессмысленно
   (перекроет созвон), свернуть тоже (смысл окна в том, что оно видно).
   Показать/скрыть — хоткеем.
6. **История выжимок — вертикальный список в отдельном окне**, не карусель:
   за час набирается больше десяти записей, листать их стрелками мучительно.
7. **Один акцентный цвет** плюс отдельные цвета статусов (хорошо / внимание /
   ошибка). Раньше акцентов было пять.
8. **Фон непрозрачный.**

## 6. Открытые вопросы — их и надо закрыть

1. **Обрезка против переноса в компактном режиме.** В макете строки обрываются
   многоточием по правому краю: при 360 px нельзя дочитать ни одного
   предложения. Позиция разработчика: переносить по словам и согласиться на
   меньшее число строк — шесть обрезанных строк хуже четырёх целых. Нужно
   решение и правило.
2. **Таймстемпы в компактном режиме.** Жёлоб съедает ~60 из 360 px, то есть
   17 % ширины. Убрать, показывать по наведению или оставить?
3. **Кнопки в компактном режиме.** Нужны ли они там вообще, если основные
   действия на хоткеях? Может быть, хватит одной — меню.
4. **Конфликт хоткея.** В макете `Alt+Space` назначен и на «показать/скрыть
   окно», и на «открыть готовую выжимку» из уведомления. Уведомление
   появляется как раз тогда, когда окно скрыто, — нужна развязка.
5. **Индикатор захвата читается наоборот.** В макете у состояния «звук есть» —
   простая точка, а осциллограмма появляется у «тишины». Интуиция обратная:
   волна = звук идёт, ровная линия = тишина. Нужна финальная логика всех трёх
   состояний.
6. **Подпись выжимки за интервал.** Хоткей `Alt+5` подписан «выжимка за 5
   минут», но интервал меняется в настройках — подпись начнёт врать.
7. **Онбординг и пустой экран конкурируют за место:** четыре подсказки плюс
   иконка и заголовок в 520×340 не помещаются. Что показываем и когда?
8. **Три состояния записи на диск** в макете не разведены — показана только
   реакция на ошибку захвата.

## 7. Что нужно на выходе

Результат заберёт разработчик. **Картинки — только дополнение; основа —
текстовая спецификация**, иначе цвета и отступы придётся угадывать по пикселям.

**1. Токены** — плоским списком «имя → значение», чтобы механически перенести в
код:

- Цвета: hex + назначение + на каком фоне используется. Отдельно: фон окна, фон
  панелей, границы, текст основной, текст вторичный, текст предварительный,
  акцент (+ ховер/нажатие), хорошо, внимание, ошибка.
- Типографика: **конкретный шрифт с поддержкой кириллицы и открытой лицензией**
  (его положат в репозиторий), плюс размеры/вес/межстрочный интервал для:
  транскрипт, предварительный текст, таймстемп, заголовок, подпись кнопки,
  вторичная подпись, статус.
- Сетка отступов: базовая единица и допустимые кратные.
- Радиусы скругления, толщины границ.
- Длительности и кривые анимаций (если они вообще нужны).

**2. Разбор каждого компонента:** размеры, внутренние отступы, все состояния
(обычное, наведение, нажатие, выключено, фокус). Компоненты: пилюля статуса,
кнопка действия, иконочная кнопка, строка транскрипта с таймстемпом, карточка
ответа модели, элемент меню, поле настроек, запись в истории выжимок, статусное
сообщение, уведомление.

**3. Раскладка в обоих размерах** — 520×340 и 360×200: что скрывается, что
сжимается, в каком порядке отваливается при сужении.

**4. Все состояния экрана:** пустой старт, живая речь, ответ модели пришёл (тот
же экран до и после — проверка на сдвиг), запись на паузе при офлайновой модели,
ошибка захвата, открытое меню.

**5. Решения по восьми пунктам §6** — коротко и однозначно.

## 8. Чего не предлагать

- Размытие того, что под окном; «стеклянные» слои; любую полупрозрачность фона.
- Тени вокруг окна.
- Веб-паттерны, которых нет в Qt Widgets: сетки с автоподбором, sticky-элементы
  внутри текстового потока, анимацию отдельных слов при появлении.
- Светлую тему (пока не нужна).
- Иконки эмодзи — только SVG или иконочный шрифт с открытой лицензией.
- Элементы без функции: лайки на ответах модели уже вырезали по этой причине —
  отправлять этот сигнал некуда.
